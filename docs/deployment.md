# QUBIT — deployment runbook (MVP1 Phase D)

Target: a reachable Next.js 15 app backed by **managed Postgres 17** with **Row-Level
Security enforced in the database**. This is what "onboard real people" requires beyond
the local `qubit_clickup` dev DB.

## 0. Prerequisites
- Node 20 LTS+, `pnpm`.
- A managed Postgres 17 instance and an **app DB role that is NOT superuser and NOT
  `BYPASSRLS`** — RLS is the tenant boundary; a superuser role silently bypasses it.
- A host for the Next.js server (container/PaaS) and a domain with TLS.

## 1. Secrets
Copy `.env.production.example` into your host's secret manager and fill every value:

| Var | Purpose |
|---|---|
| `DATABASE_URL` | Managed Postgres, pooled, `sslmode=require`, non-superuser role. |
| `AUTH_SECRET` | NextAuth signing — `openssl rand -base64 32`. |
| `AUTH_URL` | Public origin, e.g. `https://qubit.example.com`. |
| `MFA_ENCRYPTION_KEY` | Encrypts TOTP secrets at rest. Rotating it invalidates all enrolled MFA. |
| `Q_AI_BASE_URL` / `Q_AI_API_KEY` / `Q_AI_MODEL` | Q copilot — an internal OpenAI-compatible box (e.g. `qwen3-14b`). Optional; Q degrades to deterministic reports when unset. Keeps tenant data in-house. |
| `AZURE_AD_*` | Optional SSO. |

## 2. Schema + RLS
Migrations embed the RLS policies (every tenant table gets `tenant_isolation_*`), so
applying them provisions the schema **and** the security policies:

```bash
pnpm install --frozen-lockfile
pnpm prisma migrate deploy      # schema + RLS (idempotent)
pnpm prisma generate
```

Verify RLS is live before onboarding anyone:

```sql
-- every tenant table should show rowsecurity = t AND forcerowsecurity = t
SELECT relname, relrowsecurity, relforcerowsecurity
FROM pg_class WHERE relkind='r'
  AND relname IN ('user','project','team','project_member','ai_call_log','audit_log')
ORDER BY relname;
```

> **Do NOT run `pnpm prisma:seed` in production** — the seed creates synthetic demo users
> with a well-known password. Use the bootstrap script instead.

## 3. Bootstrap the tenant + first admin
Creates just the Riverbank tenant row and one `SystemAdmin` (no demo data). Idempotent.

```bash
ADMIN_EMAIL=joyce.okore@riverbank.solutions ADMIN_NAME="Joyce Okore" \
  pnpm tsx scripts/bootstrap-tenant.ts --tenant riverbank
```

It prints a one-time temp password for a **new** admin (nothing if the admin already
exists). Distribute securely; the admin resets it and enables MFA at `/settings/mfa`.

## 4. Build + run
```bash
pnpm build
pnpm start        # or your process manager / container CMD
```

Quality gates before shipping a build: `pnpm typecheck && pnpm lint && pnpm test`.

## 5. Onboard real data
Follow [`docs/onboarding/README.md`](./onboarding/README.md): fill the CSV templates,
dry-run until warning-free, `--execute`, hand off temp credentials, enable MFA, QA in the
UI, then delete `import/import-report.json`.

## 6. Post-deploy verification
- Sign in as the bootstrap admin over HTTPS.
- **Admin → Users**: only real users; MFA enabled on privileged accounts.
- Create a throwaway project, confirm **Ask Q** returns a grounded report, then remove it.
- Confirm the Q AI box is reachable (report footer says "Generated by Q", not "AI provider
  not configured") — or leave `Q_AI_*` unset to run deterministic reports.
- Cross-tenant check (if a second tenant exists): its data is invisible to Riverbank
  users (RLS test `tests/rls/*` codifies this).

## Operational notes
- **Backups + PITR** on the managed DB; test a restore.
- **Migrations**: run `prisma migrate deploy` on each release; migrations are additive and
  ship reversible `down.sql`.
- **Secrets rotation**: `AUTH_SECRET` rotation logs users out; `MFA_ENCRYPTION_KEY`
  rotation forces MFA re-enrollment — plan a window.
- **No PII in logs**: `AiCallLog` stores metrics only; keep app logs free of tenant PII.

## Docker deployment (app + Postgres)

The repo ships a production image and a Compose stack. See `Dockerfile`,
`docker-compose.yml`, `docker/db-init.sh`, `docker/entrypoint.sh`.

```bash
cp .env.production.example .env.production   # fill AUTH_SECRET, MFA_ENCRYPTION_KEY,
                                             #   AUTH_URL (your domain), Q_AI_* …
# Set the DB passwords (shell env or a compose .env) and make DATABASE_URL match:
export POSTGRES_PASSWORD=... APP_DB_PASSWORD=...
#   .env.production →  DATABASE_URL="postgresql://qubit:${APP_DB_PASSWORD}@db:5432/qubit?schema=public"
docker compose up -d --build
```

What happens:
- **`db`** (postgres:17) runs `docker/db-init.sh` once on first boot: it creates the
  **non-superuser** `qubit` role and gives it ownership of the DB + `public` schema.
- **`app`** builds the standalone image; its entrypoint runs `prisma migrate deploy`
  (schema **+** RLS policies, idempotent) then serves on `:3000`.

**Why a non-superuser role matters:** every tenant table uses `FORCE ROW LEVEL SECURITY`,
so even the table owner is subject to the `tenant_isolation_*` policies. A superuser (or a
`BYPASSRLS`) role would silently ignore them and defeat tenant isolation. `db-init.sh`
provisions the role correctly; keep `DATABASE_URL` pointed at it, never at `postgres`.

**First deploy — bootstrap the first admin** (not the demo seed):

```bash
docker compose run --rm --entrypoint sh app -c \
  'ADMIN_EMAIL=you@yourco.com ADMIN_NAME="You" npx tsx scripts/bootstrap-tenant.ts --tenant riverbank'
```

**TLS / domain:** terminate TLS at your reverse proxy (Caddy / Nginx / Traefik / cloud LB)
and proxy to the `app` container's `:3000`. `AUTH_URL` must be the public `https://…` origin
(NextAuth builds callback URLs from it). Point the proxy's upstream at `app:3000` on the
Compose network, or publish `APP_PORT` and proxy to the host.

**Managed Postgres instead of the `db` service:** drop the `db` service, set `DATABASE_URL`
to the managed instance (non-superuser role, `sslmode=require`), and ensure that role owns
the schema (or run migrations as an owner). Everything else is unchanged.

> Note: the image is built without Docker available in CI here — build it once in your
> pipeline (`docker compose build`) and run the quality gates (`pnpm typecheck && pnpm lint
> && pnpm test`) before publishing.

## Scheduled jobs (M1+)

The app exposes `POST /api/internal/cron` (guarded by `CRON_SECRET`, DM1.15 №4). The
box's crontab drives it — one line per job. Nightly snapshots (KPI sparklines, delta
feed, M2 check-in drafts) run at 23:55 East Africa Time:

```cron
55 23 * * * curl -sS -X POST https://q.fikrawork.com/api/internal/cron \
  -H "Authorization: Bearer $CRON_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"job":"nightly-snapshot"}' >> /home/osbui/applications/qubit/cron.log 2>&1
```

The default idempotency key is `<job>:<UTC date>`, so a re-delivered hit within the same
day is a recorded no-op (`status: "Skipped"`). Set `CRON_SECRET` in the box's
`.env.production` and export it in the crontab environment.

The M2 weekly loop adds two Friday jobs — drafts in the morning, the report in the
afternoon (after leads have had the day to confirm):

```cron
0 8 * * 5 curl -sS -X POST https://q.fikrawork.com/api/internal/cron \
  -H "Authorization: Bearer $CRON_SECRET" -H "Content-Type: application/json" \
  -d '{"job":"friday-checkin-drafts"}' >> /home/osbui/applications/qubit/cron.log 2>&1
0 16 * * 5 curl -sS -X POST https://q.fikrawork.com/api/internal/cron \
  -H "Authorization: Bearer $CRON_SECRET" -H "Content-Type: application/json" \
  -d '{"job":"friday-report"}' >> /home/osbui/applications/qubit/cron.log 2>&1
```
